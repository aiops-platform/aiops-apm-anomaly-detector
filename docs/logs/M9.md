# M9 实现日志：日志异常按 signature / traceId 分组出单（跨服务合并）

**状态：** 已完成（`make lint` 干净、`make test` 516 通过 + 26 skip、`make test-pg` 26 通过）
**动机：** M0–M8 期间 `run_domain` 把一轮内异常**按 service 分组**，每服务一条 `problem_record`。后果有两个方向都不对：
一个服务报 3 类不同错误只得到 1 条记录（根因/处理方式/误报率都不同，混在一起无法分别关单）；反过来，同一次请求失败在多处打的日志（共享业务 `traceId`，可能跨服务）本质是一个事故，却按服务裂成多条。

## 落地形态

`pipeline/runner.run_domain` 不再按 service 切，改为按 **`grouping.group_anomalies` 划分出的「事故组」**出单。

分组规则是**连通分量**：

| 连线 | 说明 |
|---|---|
| 同 `signature` | 同一类问题 |
| `trace_ids` 相交 | 同一次请求失败（**可跨服务**） |
| metric → 本服务的日志组 | 保住「同源 metric+log 升 critical」（见下方条件） |

| 场景 | 结果 |
|---|---|
| 3 个不同 traceId，同一签名 | 1 条 |
| 1 个 traceId，3 类不同错误 | 1 条，evidence 列出 3 个签名 |
| 不同签名、无共同 traceId | 多条 |
| traceId 跨 3 个服务 | 1 条，`service` = `"gateway-service,order-service,warranty-service"` |

**为什么用连通分量而不是「traceId 优先，无 traceId 才按 signature」**：后者会让「同一签名跨 3 个 traceId」裂成 3 条，与「同一类问题应是一条」冲突。

## 顺带修掉的两个既有缺陷

### 1. `signature_aggregate` 在校验前就跨服务塌陷了

```python
groups.setdefault(sig, []).append(s)   # 只用 signature 分组，不含 service
...
service=logs[0].service                 # 取第一条的 service —— 取决于 ctx.signals 插入顺序
```

两个服务打出同一签名时会塌成**一条** `LogAnomaly`，`service` 取到谁看运气，`count` 却是跨服务总数。
而 `fingerprint.anomaly_key = log|tenant|service|signature` 把这个**任意**的 service 焙进了去重身份
→ `detection_state` 的持续性计数与 `reconcile` 的 miss 判定会在服务间漂移。

**已修**：分组键改成 `(signature, service)`。

### 2. `service` 列的宽度不够

`problem_record.service` 原是 `VARCHAR(64)`，只装得下一个服务名。多服务拼接（如 5 个服务 ≈ 80 字符）
会报 22001（value too long）→ **整轮采集失败**。V10 加宽到 255。

## 五个静默破坏点与对策

这几条现有测试**一个都抓不到**，逐条设了防：

| # | 风险 | 后果 | 对策 |
|---|---|---|---|
| 1 | `seen_keys` 覆盖：异常漏进/重复进 `l3_verify` | 漏 → `sweep` 每轮 `miss_rounds+1` → **reconciler 自动关掉活着的单**；重复 → `consecutive_rounds` 双增 → 持续性闸门被绕过 | `group_anomalies` 是**划分**（结尾断言并集==全集、两两不交）；`test_m9_seen_keys_covers_every_anomaly` + `test_grouping.py` 的不变量测试 |
| 2 | `ProblemRecord.group_key` 不稳 | 代表服务每轮变 → 去重失效、重复开单、`fpr_table` 条目成孤儿、误报率闸门静默失效 | 代表 = 排序后第一个服务名；`test_m9_group_key_stable_across_rounds` + `test_representative_service_stable_across_rounds` |
| 3 | `records_by_service` 算术 | 只记代表服务 → 其它 target 显示 `anomaly_count>0, record_count=0`，与「还没到持续性轮次」**无法区分** | 改为 credit-all；且**用 `+=` 而非赋值**（同 service 可能有多个组，赋值会覆盖） |
| 4 | `related` 语义 | `calibrate_severity` 从不检查 service，「同服务」的保证原先只靠调用方按 service 分组；分组跨服务后会让**不相干的 metric/log 配对**升 critical | `_within_window` 显式限定同 service 配对；`test_m9_cross_service_metric_log_not_related` 构造了唯一可达的误判路径 |
| 5 | `signature_aggregate` 跨服务塌陷 | 见上 | 分组键加 service |

## `group_key` 与 M1 冻结契约

`fingerprint.group_key(tenant, domain, service, anomalies)` **没改**（M1 冻结）。

但 `ProblemRecord.group_key` 属性原本用 `self.service` 算——拼接串会连带
`group_key` / `open_group_key`（生成列）/ `uk_open_group_key` 索引**三处都要加宽**。

**对策**：给 `ProblemRecord` 新增**可选字段** `group_key_service`（冻结契约明确允许「增加可选字段」），
属性优先用它。`emit` 传排序后的第一个服务名（组代表，≤64），于是只需加宽 `service` 一列。
对外可见的 `service` 列仍是完整拼接串，两者语义解耦。

## metric 与多日志组的歧义处理

metric 异常挂到本服务日志组，**但仅当该服务的日志异常同属一个分量时**。若该服务有多个日志组
（多类 error 各自成单），metric 自成一組——否则「并入全部」会把不同类型的日志组强行并成一条记录，
恰是 M9 要避免的。这个条件在 `grouping.group_anomalies` 里显式注释。

## 补充：`detection_type` 派生字段（M9 之后）

`problem_record` 没有显式的检测来源列（`source` 是模块名，固定 `apm-alert`）。类型由证据推出：
`log` / `metric` / `combined` / `unknown`（`router/problems.py` 的 `_detection_type`），**列表与详情都返回**。

**刻意派生而非入库**：存列会与证据漂移（改了 anomaly 忘了同步列），派生不可能不一致，也免了迁移与回填。
实现时踩到一个坑——`_strip_decision_snapshots` 在无需剥离时返回的是**同一个 dict 对象**，而 InMemory store
的 `list()` 给的就是库内对象，原地加字段会把"派生"变成"隐式入库"。故两处都构造新 dict，
并有 `test_detection_type_does_not_mutate_stored_record` 守着。

## 遗留

- **端到端未验证「注入 ERROR → 开单」全链路**：现网 `app-logs` 实测 **108 INFO / 1 WARN / 0 ERROR**，
  检测器匹配 `ERROR` 级，所以真实链路跑出来是 0 条记录（符合预期）。要验证需先跑测试床的场景脚本注入 ERROR——
  那会改动测试床状态，交由使用者决定时机。
- 检测器 matcher 现为字符串 `"ERROR"`（等价 `level == "ERROR"`）。若日后要收 WARN 或按服务细分，
  换成结构化 matcher `{"signal_type": "log", "level": ..., "service": ...}` 即可（`filter_signals` 已支持）。
- `l3_verify` 里 fpr 键用 `persisted` 而记录 `group_key` 用全部异常——两者在
  `persistence_rounds=1` 下恒等，故当前无影响；若日后把轮次闸门调回 ≥2，需重新审视（届时 fpr 读写键会不一致）。
