# M9 实现日志：日志异常按 signature / traceId 分组出单（跨服务合并）

**状态：** 已完成（`make lint` 干净、`make test` 516 通过 + 26 skip、`make test-pg` 26 通过）
**动机：** M0–M8 期间 `run_domain` 把一轮内异常**按 service 分组**，每服务一条 `problem_record`。后果有两个方向都不对：
一个服务报 3 类不同错误只得到 1 条记录（根因/处理方式/误报率都不同，混在一起无法分别关单）；反过来，同一次请求失败在多处打的日志（共享业务 `traceId`，可能跨服务）本质是一个事故，却按服务裂成多条。

## 落地形态

`pipeline/runner.run_domain` 不再按 service 切，改为按 **`grouping.group_anomalies` 划分出的「事故组」**出单。

分组规则是**连通分量**：

| 连线 | 说明 |
|---|---|
| 同 `signature` | 同一类问题 |
| `trace_ids` 相交 | 同一次请求失败（**可跨服务**） |
| metric → 本服务的日志组 | 保住「同源 metric+log 升 critical」（见下方条件） |

| 场景 | 结果 |
|---|---|
| 3 个不同 traceId，同一签名 | 1 条 |
| 1 个 traceId，3 类不同错误 | 1 条，evidence 列出 3 个签名 |
| 不同签名、无共同 traceId | 多条 |
| traceId 跨 3 个服务 | 1 条，`service` = `"gateway-service,order-service,warranty-service"` |

**为什么用连通分量而不是「traceId 优先，无 traceId 才按 signature」**：后者会让「同一签名跨 3 个 traceId」裂成 3 条，与「同一类问题应是一条」冲突。

## 顺带修掉的两个既有缺陷

### 1. `signature_aggregate` 在校验前就跨服务塌陷了

```python
groups.setdefault(sig, []).append(s)   # 只用 signature 分组，不含 service
...
service=logs[0].service                 # 取第一条的 service —— 取决于 ctx.signals 插入顺序
```

两个服务打出同一签名时会塌成**一条** `LogAnomaly`，`service` 取到谁看运气，`count` 却是跨服务总数。
而 `fingerprint.anomaly_key = log|tenant|service|signature` 把这个**任意**的 service 焙进了去重身份
→ `detection_state` 的持续性计数与 `reconcile` 的 miss 判定会在服务间漂移。

**已修**：分组键改成 `(signature, service)`。

### 2. `service` 列的宽度不够

`problem_record.service` 原是 `VARCHAR(64)`，只装得下一个服务名。多服务拼接（如 5 个服务 ≈ 80 字符）
会报 22001（value too long）→ **整轮采集失败**。V10 加宽到 255。

## 五个静默破坏点与对策

这几条现有测试**一个都抓不到**，逐条设了防：

| # | 风险 | 后果 | 对策 |
|---|---|---|---|
| 1 | `seen_keys` 覆盖：异常漏进/重复进 `l3_verify` | 漏 → `sweep` 每轮 `miss_rounds+1` → **reconciler 自动关掉活着的单**；重复 → `consecutive_rounds` 双增 → 持续性闸门被绕过 | `group_anomalies` 是**划分**（结尾断言并集==全集、两两不交）；`test_m9_seen_keys_covers_every_anomaly` + `test_grouping.py` 的不变量测试 |
| 2 | `ProblemRecord.group_key` 不稳 | 代表服务每轮变 → 去重失效、重复开单、`fpr_table` 条目成孤儿、误报率闸门静默失效 | 代表 = 排序后第一个服务名；`test_m9_group_key_stable_across_rounds` + `test_representative_service_stable_across_rounds` |
| 3 | `records_by_service` 算术 | 只记代表服务 → 其它 target 显示 `anomaly_count>0, record_count=0`，与「还没到持续性轮次」**无法区分** | 改为 credit-all；且**用 `+=` 而非赋值**（同 service 可能有多个组，赋值会覆盖） |
| 4 | `related` 语义 | `calibrate_severity` 从不检查 service，「同服务」的保证原先只靠调用方按 service 分组；分组跨服务后会让**不相干的 metric/log 配对**升 critical | `_within_window` 显式限定同 service 配对；`test_m9_cross_service_metric_log_not_related` 构造了唯一可达的误判路径 |
| 5 | `signature_aggregate` 跨服务塌陷 | 见上 | 分组键加 service |

## `group_key` 与 M1 冻结契约

`fingerprint.group_key(tenant, domain, service, anomalies)` **没改**（M1 冻结）。

但 `ProblemRecord.group_key` 属性原本用 `self.service` 算——拼接串会连带
`group_key` / `open_group_key`（生成列）/ `uk_open_group_key` 索引**三处都要加宽**。

**对策**：给 `ProblemRecord` 新增**可选字段** `group_key_service`（冻结契约明确允许「增加可选字段」），
属性优先用它。`emit` 传排序后的第一个服务名（组代表，≤64），于是只需加宽 `service` 一列。
对外可见的 `service` 列仍是完整拼接串，两者语义解耦。

## metric 与多日志组的歧义处理

metric 异常挂到本服务日志组，**但仅当该服务的日志异常同属一个分量时**。若该服务有多个日志组
（多类 error 各自成单），metric 自成一組——否则「并入全部」会把不同类型的日志组强行并成一条记录，
恰是 M9 要避免的。这个条件在 `grouping.group_anomalies` 里显式注释。

## 补充：日志 target 按级别过滤（M9 之后）—— 采集被 INFO 洪峰卡死

**触发**：一条 ERROR 日志（traceId `e1034ca7-...`）没进 `problem_record`，排查发现**问题不在漏斗，在采集**。

### 卡死机制（实测数据）

采集器每轮下发 `[水位线, now]`、按 `@timestamp` **升序**、`size` 默认 **500**，水位线只推进到**本页 500 条的最大时间**
（`collectors/http_logs.py:60,62,151-152`）。而源端有巨量突发：

| 时刻 | 量 |
|---|---|
| 05:31:52（0.7 秒内） | 约 40,000 条 |
| 05:33:30 | 约 72,926 条 |
| 该 ERROR 之前积压 | **111,418 条** |

水位线 6 轮只挪了 **83 毫秒**（`05:31:52.086 → .169`），滞后 569 秒且持续扩大 —— 按 500 条/轮 ≈
**223 轮 ≈ 4 小时**才轮到那条 ERROR。各轮审计一律 `status=ok signals=500 anom=0`，**与正常运行无法区分**，
且 `metrics.py` 里没有水位线滞后指标。这是本次最值得记住的一点：**饱和（打满 size）是个静默故障**。

次因：`signature_aggregate` 的 `min_count=5` 要求同签名在一轮内 ≥5 条。该处日志密度 **53~68 条/毫秒**，
500 条切片只覆盖 **7~9 毫秒**，而同签名的 6 条 ERROR 跨 2.7 秒 —— 每轮切片最多命中 1~3 条，凑不满 5。
（对照：`PR-20260923-0001` 是 14 条同签名 NPE 撞进同一轮，所以开得出来。）

### 两条实测死路（别再走）

| 做法 | 结果 |
|---|---|
| `source_config.params` 放过滤键 | ES **400** `unrecognized parameter: [level]` → 整轮采集 failed |
| `params: {"q": "app.level.keyword:ERROR"}` | HTTP 200，但 **`q` 整体替换 body 的 `query`**（body 的 `size`/`sort` 保留）→ 水位线窗口与服务隔离**静默失效**。实测同一 body：不带 `q` 返回窗口内 10000 条；带 `q` 返回 31 条且**全在窗口之外** |

### 落地形态

`source_config` 新增两个键（生成 `terms` filter **追加**进 `bool.filter`，不替换既有过滤）：

```json
"level_field": "app.level.keyword",
"levels": ["ERROR"]
```

同步把 `_build_body` 的 ES 模式启用条件与 `collect()` 的 `es_mode` 都加上 `level_field`
（否则"只设 level_field"的 target 会拿到 `None` body、或把时间窗降级成 URL 参数 → 400）。

**两条静默归零的坑已设防**（都实测过）：
- `{"terms": {field: []}}` 匹配 **0 条** → `levels` 为空时**不下发**该 filter；
- `list("ERROR")` 会碎成 `['E','R','R','O','R']` → 裸字符串按单元素列表处理。

取值须与源端**大小写完全一致**（`.keyword` 是精确 term，实测 `["error"]` 匹配 0 条）。实现不强行 `upper()`——
源侧取值大小写不可假定，宁可让配置显式写对。

**改动清单**：`collectors/http_logs.py`（`_build_body` + `es_mode` + docstring）、`tests/test_collectors.py`
（新增 6 条：过滤追加 / 无键不回归 / 空 levels 三种变体不下发 / 裸字符串不碎）、
`docker/seed_testbed_logs.py`（三条 target 加键 + docstring 里过期的"0 ERROR"结论）、
`docs/operational-guide.md` §3.2 键表（顺带补齐一直缺文档的 `time_field`/`service_field`/`level_field` 一行）、`README.md`。

## 补充：Analyze 起 run 稳定 502 —— 10 秒超时 vs agentflow 同步准备工作区（M9 之后）

**触发**：Problem Center 点「分析」报失败，访问日志只有 `POST /v1/problems/PR-20260923-0002/analyze → 502 Bad Gateway`。

### 定位过程（含一次走错路，记下来）

1. **502 是我们自己返回的**：`_app.py` 的 `ErrorCode.UPSTREAM: 502`。`problems.py` 把 agentflow 的
   **任何 ≥300** 折叠成 UPSTREAM，所以 429 / 500 / 超时**长得一模一样**。
2. **第一次推断错了**：从响应体的空 reason（`"agent workflow run start failed: "`）出发，
   我先认定是租户并发配额满（429）。当时确实查到 `otr` 租户有 **8 个非终态 run 永久占着 10 个并发槽位**
   （7 个 `waiting_approval` 最老到 5 天前 + 1 个挂了一天多的 `running`），而且
   **它们没有任何 API 路径能清掉** —— `POST /runs/{id}/stop` 在 queue 模式下只入队一条命令，
   而这些 run 早无 executor，内存队列里的命令没人消费即丢失，接口却照样返回 `{"ok": true}`。
   清掉这 8 个（直接改 `otr.db`）是真的解了槽位泄漏，**但它不是这个 502 的原因**。
3. **真因**：重发 analyze 并计时 → **10.016s**，与 `APM_OUTBOUND_TIMEOUT_SEC=10.0` 分毫不差。
   `httpx.ReadTimeout` 的 `str()` **是空的**，所以 reason 只剩冒号 —— 这个"空字符串"正是
   把排查带偏的东西。而 agentflow 慢在：`service.py::_create` 在 `POST /run` **返回之前**
   同步 `await self._prepare_workspace(...)`（拉修复侧仓库），实测 >10s。
4. **最恶劣的后果**（实测复现）：超时**不阻止** agentflow 把 run 跑起来。两次"失败"的 analyze
   各在 agentflow 留下一个真 run（其一 `running`），而超时走异常分支 → **不写 run 绑定** →
   记录仍是 `pending` → 用户看到失败就再点 → **每点一次多一个孤儿 run，且都占并发配额**。
   这与最初观察到的"66 秒内三次点击、三个 run"完全吻合。

### 改动（本仓）

- `settings.py` 新增 **`run_start_timeout_sec`（默认 60s）**：起 run 专用，**不共用**
  `outbound_timeout_sec`（后者 10s，是采集器在用，放宽它会连带影响采集）。
- `problems.py`：`analyze_problem` 与 rerun 两处 `POST /run` 传 `timeout=`，并**先捕
  `httpx.TimeoutException`**，用独立文案 `_RUN_START_TIMEOUT_REASON` —— 明确写"run 很可能
  已在后台跑，重试会再起一个"。（两处共用常量，理由同 `_TERMINAL_STATES` 的防漏注释。）
- `_app.py` 的 `AppException` 处理器**补日志**：UPSTREAM 走 `warning`，其余 `info`。
  此前它只返回 JSON，`reason` 只存在于响应体，库里与访问日志里都没有 —— 这就是上面第 2 步
  只能靠"空字符串"反推的原因。
- `tests/test_problem_analyze_api.py`：新增 3 条 —— 专用超时被下发、超时文案可识别且点明勿重试、
  上游失败留日志；`CapturingHttp` 增记 `timeout`，新增 `TimeoutHttp`（**刻意复现空消息**的 `ReadTimeout`）。
