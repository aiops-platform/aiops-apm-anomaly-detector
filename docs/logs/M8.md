# M8 实现日志：存储层 PostgreSQL 化

**状态：** 已完成（`make lint` 干净、`make test` 490 通过 + 22 skip、`make test-pg` 512 通过）。
**动机：** 本模块要接入的 `multi-agent-workflow` docker compose 里只有 PostgreSQL，没有 MySQL。继续用 MySQL 意味着额外维护一个数据库容器，与本平台既有中间件割裂。
**范围：** 把存储层从 MySQL/`aiomysql` 整体换成 PostgreSQL/`psycopg3`，复用该 compose 已有的 PG 实例。

## 前置事实（决定了方案形态）

迁移前实测 MySQL 现状：`schema_versions` 已有 8 条记录（V1–V8 全部应用过），但**业务表全部 0 行**（仅 `scheduler_lease` 有 1 行心跳）。
→ **没有数据需要迁移**，V1–V8 直接原地改写为 PG 方言，不需要写「V9 移植」迁移。

顺带纠正了 `docs/project-overview.md` 的过期记录：backlog 里「MySQL 真库实测（本机未运行）」实际早已跑过。

## 落地形态

| 项 | 值 |
|---|---|
| 驱动 | `psycopg[binary,pool]>=3.2`（取代 `aiomysql`） |
| 库 | `agentflow`（复用 multi-agent-workflow 的 PG 实例） |
| schema | 独立 schema `aiops_apm_runtime`（`APM_DB_SCHEMA`），与同库 agentflow 的 `public` 表隔离 |
| 后端开关 | `storage_backend: "pg" \| "memory"`（`mysql` 已下线，`build_storage` 遇 `mysql` 抛 `ValueError`） |
| 时间列 | `TIMESTAMP(3)`（无时区），库内约定存 **naive UTC** |
| 类名 | `MySQL*Store` → `PG*Store`（10 个） |

选 psycopg3 而非 asyncpg：psycopg3 保留 `%s` 占位符，~76 处 SQL 参数零改动，只需改 MySQL 专有语法；asyncpg 的 `$1` 序号制要重排全部占位符，机械但易错位。

## 方言映射（改存储层时对照此表）

### DDL

| MySQL | PostgreSQL |
|---|---|
| `CREATE DATABASE ... / USE x` | 由 `MigrationRunner` 按 `settings.db_schema` 注入 `CREATE SCHEMA` + `SET search_path` |
| `BIGINT AUTO_INCREMENT PRIMARY KEY` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| `DATETIME(3)` | `TIMESTAMP(3)` |
| `TINYINT(1)` | `SMALLINT`（**不用 `BOOLEAN`**：代码里有 `WHERE deleted=0`，PG 的 `boolean = integer` 直接报错） |
| `JSON` | `JSONB` |
| `DOUBLE` | `DOUBLE PRECISION` |
| `COMMENT '...'` | 独立 `COMMENT ON COLUMN/TABLE ... IS '...'` |
| `ENGINE=InnoDB` | 删除 |
| 表内 `INDEX` / `UNIQUE KEY` | 独立 `CREATE INDEX IF NOT EXISTS` / `CONSTRAINT ... UNIQUE` |
| `ADD COLUMN x ... AFTER y` | 删掉 `AFTER`（PG 无列序概念） |
| `MODIFY COLUMN x VARCHAR(1024)` | `ALTER COLUMN x TYPE VARCHAR(1024)` |
| `` `signal` `` | `"signal"` |
| `ON UPDATE CURRENT_TIMESTAMP(3)` | `set_updated_at()` 触发器 + 逐表 `DROP TRIGGER IF EXISTS` + `CREATE TRIGGER` |
| `GENERATED ALWAYS AS (...) STORED` | 原样保留（PG 12+ 支持，表达式 immutable） |

### DML

```sql
INSERT ... VALUES (...) AS new ON DUPLICATE KEY UPDATE c = new.c
→ INSERT ... VALUES (...) ON CONFLICT (<冲突列>) DO UPDATE SET c = EXCLUDED.c
```

| 位置 | 写法 |
|---|---|
| `sequence.next_id` | `ON CONFLICT (seq_date) DO UPDATE SET next_seq = record_seq.next_seq + 1 RETURNING next_seq` |
| `lease.try_acquire` | `ON CONFLICT (lease_name) DO UPDATE SET holder = CASE WHEN ... END ... RETURNING holder` |
| `lease.renew` | `CURRENT_TIMESTAMP(3) + make_interval(secs => %s)`（**不能写 `+ %s`**，float 绑不成 interval） |
| `records.write_or_append` | `COALESCE(evidence,'[]'::jsonb) \|\| EXCLUDED.evidence` |
| `records.mark_in_progress` / `append_evidence` | `COALESCE(evidence,'[]'::jsonb) \|\| jsonb_build_array(%s::jsonb)` |
| `detection_state.sweep` | `jsonb_set(state_value,'{miss_rounds}', to_jsonb((state_value->>'miss_rounds')::int + 1))` |
| 严重度升级 | `FIELD()` → `COALESCE(array_position(ARRAY['warning','high','critical'], x), 0)` |
| `execute_lastid` | → `execute_returning`（`cursor.lastrowid` 在 psycopg3 不存在，改用 `RETURNING`） |

## PG 专属陷阱（本次实际踩到或差点踩到的）

这几条都**不报错**或报错位置极具误导性，是本次迁移的主要风险来源。

1. **整数除法让 FPR 闸门静默失效。** `fpr = (false_positive_cnt + %s) / (total_cnt + 1)` 在 PG 是 `bigint/bigint` **整数除法**（MySQL 的 `/` 恒返回 DECIMAL），漏掉 `::numeric` 会让 `fpr` 恒为 0 或 1 —— 不报错，但 L3 的误报率闸门按错误的值判定。已在集成测试里用 1/3 锁定。

2. **会话时区会让 naive 时间戳差 8 小时。** 目标 PG 容器设了 `TZ: Asia/Shanghai`。PG 的 `CURRENT_TIMESTAMP` 返回 `timestamptz`，写进 naive `TIMESTAMP(3)` 列时按**会话时区**折算；而 psycopg3 对 aware datetime 也走 `timestamptz`（同样折算），对 `_iso()` 字符串则走 unknown OID（offset 被忽略、原样写入）。同一个 `trace_id` 的 `detection_round.started_at`（字符串路径）与 `problem_record.detected_at`（datetime 路径）会因此相差 8 小时。
   → 对策：连接串固定 `-c TimeZone=UTC`，并在 `_ConnectionHandle` 内把 aware datetime 归一为 naive UTC 兜底。实测偏差已 < 1s。

3. **`execute(sql, ())` 会触发 psycopg3 的 `%` 扫描。** 传非 `None` 的 `params` 时 psycopg 会扫描整条 SQL 找 `%` 占位符，遇到裸 `%` 抛 `ProgrammingError`，且**不认字符串字面量里的 `%`**。aiomysql 只在 args 为真值时才格式化，所以传 `()` 一直无害——这是 PG 引入的新失败模式，而本仓库 DDL 含大量 `COMMENT ON ... IS '...'`。
   → 对策：`_ConnectionHandle._run` 里 `if args: cur.execute(sql, args) else: cur.execute(sql)`。

4. **`Jsonb` 不在构造时序列化，且默认 `json.dumps` 无 `default` 钩子。** JSON 列里有 datetime（emit 的 `metric_anomalies.detected_at`），直接 `Jsonb(dict)` 会把一个原本在调用点立刻抛的 `TypeError` 推迟到 `cur.execute` 里才炸——即每次 `write_or_append`。
   → 对策：`Jsonb(value, dumps=lambda o: json.dumps(o, ensure_ascii=False, default=_default))`。

5. **`jsonb_set` 的路径必须是数组形态。** 写成 MySQL 的 `'$.miss_rounds'` 不报错——它会创建一个**名为 `$.miss_rounds` 的新键**，于是 `miss_rounds` 永远不动，reconcile 的自动关单静默失效。

6. **`ON CONFLICT DO UPDATE` 里别把裸列改成 `EXCLUDED.`。** PG 中表名限定的右侧引用取**更新前的行**（正是累计值需要的），`EXCLUDED` 是本次插入值。机械替换会让 `version = version + 1` 变成恒为 2、`false_positive_cnt + %s` 变成 `fp_inc + fp_inc`。

7. **索引名在 PG 是 schema 级（MySQL 是表级）。** 原 V1 的 `idx_tenant_service_time` 在 `change_record` 与 `maintenance_window` 上重名，第二条 `CREATE INDEX` 报 `42P07`；又因 PG 的 DDL 是事务性的，**整个迁移回滚**。`maintenance_window` 上的已改名 `idx_tenant_service_window`。

8. **迁移脚本不得写死 schema。** MySQL 版靠 `USE aiops_apm_runtime` 选库，库名恒等于 schema 名所以能写死。PG 的 schema 是可配置的（`APM_DB_SCHEMA`）——脚本里一旦出现 `SET search_path`，执行瞬间就把 runner 设的 search_path 切走，建表落到别的 schema，`INSERT INTO schema_versions` 还会撞主键。默认配置下两个名字相同、问题被掩盖。已加回归测试守住。

9. **`CREATE TRIGGER` 在 PG 17 没有 `IF NOT EXISTS`**，可重入靠 `DROP TRIGGER IF EXISTS` 前置。

10. **`_as_json` 仍须包一层。** 裸 `dict` 在 psycopg3 没有 dumper（`cannot adapt type 'dict'`）；而传 `str` 反而能work（走 unknown OID），但会让 `jsonb_build_array(%s)` 退化成 JSON **字符串**元素。

11. **大小写敏感性。** MySQL 的 `utf8mb4_unicode_ci` 大小写**不敏感**，PG 默认**敏感**。影响 `uk_tenant_domain`（`Application` 与 `application` 会变成两行启用配置 → 同一个 domain 每轮跑两遍）、`scheduler_lease` 主键（副本互斥可被大小写差异绕过），以及直接透传的 `X-Tenant-Id`（`Default` 查不到 `default` 的数据）。
    → 对策：在租户入口（`router/deps.get_tenant_id` 与 `auth/middleware` 的 scope 比对）统一归一为小写。

12. **就绪探针会说谎（已修）。** PG 下库是共享的，schema 缺失时**连接照样成功**——只探 `SELECT 1` 会让服务正常启动、`/ready` 报 `ready`，而每个真实查询都 500（`relation "monitor_target" does not exist`）。MySQL 时代库不存在时连接本身就失败，所以没有这个问题，**这是 PG 化引入的回归**。
    → 对策：`ConnectionPool.schema_ready()` 用 `to_regclass('problem_record')` 探 search_path 可见性；`build_storage` 在返回前调它，不通过就带明确指引抛错。**该检查不能下沉到 `ConnectionPool.init()`**——迁移执行器要连一个 schema 还不存在的库去建它，放那儿会自锁。

13. **DDL 事务性带来的运维差异。** MySQL 下 DDL 隐式提交，中途失败留半截 schema；PG 下整轮是一个事务，任一条失败回滚全部（含 `schema_versions` 记录）。这是改进，但操作员看到的现象不同。
